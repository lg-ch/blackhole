## Phase 2 : storage chained-blocks (2026-05-13)

### Pourquoi
Pour scaler à 1B docs, la phase **sort** (qui charge tout le fichier d'un arbre + sort + counts ≈ 24 MB par arbre à 1M docs, → 24 GB à 1B docs/arbre) devient impossible. Les chained-blocks éliminent le sort.

### Format

Bloc fixe de 32 bytes :
```
struct Block { uint32 count; uint32 doc_id[6]; uint32 next; }
```

Par arbre, un fichier `tree%05d.bks` :
- bloc 0 = sentinel (zeros)
- blocs 1..n_leaves = racines (offset = leaf_id × 32)
- blocs n_leaves+1.. = overflow alloués à la volée

`next = 0` signifie fin de chaîne.

### Validation depth 18

Avant de coder, vérifié que depth 18 donne **meilleure recall que depth 21** (256K leaves, 4 docs/leaf en moyenne — plus dense, moins de bruit) :

| Depth | recall@10 | build | ms/q |
|---|---|---|---|
| 21 sort | 99.37% | 269 s | 16 |
| **18 sort** | **99.77%** | 243 s | 19 |

→ Profondeur cible : 18.

### Implémentation
- `src/block_store.{h,c}` : primitives bloc (create/open/read/write/alloc, mmap-only en lecture)
- `src/build_tree.c` : `convert_tree_to_blocks` remplace `sort_tree_file`. Lit le pair-file scratch, écrit le blocks-file, supprime le pair-file.
- `src/query_tree.c` : `vote_leaf` itère la chaîne de blocks au lieu de binary-search.

### Résultats (SIFT 1M, depth 18, 1000 trees, sub16, v3, top_n=500)

| Storage | recall@10 | ms/q | RssAnon | RssFile (cache OS) | peak ru_maxrss | scale 1B |
|---|---|---|---|---|---|---|
| Sort | 99.77% | 19 | 3.5 MB | (cache OS) | 20 MB | ✗ (sort blow-up) |
| **Blocks + mmap** | **99.77%** | **54** | **0.14 MB** | 6.3 GB | 6.3 GB | ✓ |
| Blocks + pread | 99.77% | 194 | 3.6 MB | 0 | 3.6 MB | ✓ |

Convert phase peak RSS = **13 MB** (vs sort phase 20 MB).

### Interprétation du RSS

`ru_maxrss` inclut les pages fichier mappées (`RssFile`), qui sont du page cache OS. Sur une machine à mémoire contrainte, l'OS éviction limite naturellement `RssFile` au budget cache disponible — c'est **partagé OS-wide**, pas du privé du process.

**Le vrai compteur "RAM privée" = `RssAnon` = 0.14 MB**. L'objectif "RAG quasi-zéro RAM" est atteint.

### Trade-off

- **Sort** wins sur la latence query au scale 1M (19 ms) mais ne scale pas (sort RAM explose).
- **Blocks+mmap** est légèrement plus lent (54 ms) mais scale parce que :
  - Convert phase RAM = O(n_leaves × bloc), pas O(n_docs)
  - Query lit O(1) blocs par arbre par query (vs O(log n) preads pour binary-search)
  - File-backed RSS est OS-managed, pas dans le quota privé

### Hypothèse à vérifier plus tard
La convert phase actuelle fait beaucoup de `pwrite` random (~300K par arbre). Une variante "tout en RAM puis 1 gros pwrite séquentiel" devrait diviser le convert par 5× sans changer le pic RAM.

## Phase 3 : K-way merge (élimine le votes[n_docs])

### Problème
`forest_collect_topn` faisait `uint16_t votes[n_docs]++` à chaque hit, puis scan complet pour top-N. À 1M docs : 2 MB RAM privée. **À 1B docs : 2 GB → impossible.**

### Solution
K-way merge streaming sur les chaînes triées des arbres :
- Les doc_ids dans chaque chaîne sont triés croissants par construction (build streaming en ordre doc_id).
- 1 curseur par arbre, min-heap sur leur tête (le doc_id courant).
- À chaque pop, on compte les occurrences du même doc_id (= votes pour ce doc), on push (doc, count) dans un min-heap de top-N.

### Implémentation
`forest_collect_topn` réécrit dans `query_tree.c` : `TreeCursor[n_trees]` + heap de pointeurs + heap top-N par votes. Le param `votes_scratch` supprimé de la signature.

```
Budget anonyme (1000 trees, top_n=500):
  cursors  = 1000 × 80 bytes  =  80 KB
  cheap    = 1000 × 8 (ptr)   =   8 KB
  topn_h   =  500 × 8         =   4 KB
  scratch  = ~1 KB
  Total < 100 KB, indépendant de n_docs
```

### Résultats SIFT 1M, depth 18, 1000 trees, sub16 v3, top_n=500

| Variante | recall@10 | peak RssAnon | RssFile | ms/q | scale 1B |
|---|---|---|---|---|---|
| Votes array + mmap | 99.77% | ~2 MB | 6.3 GB | 54 | **RssAnon → 2 GB** ✗ |
| **K-way merge + mmap** | **99.77%** | **228 KB** | 5.7 GB | 125 | **RssAnon → 228 KB** ✓ |

→ RAM privée **constante avec n_docs**. Coût : query 2× plus lent (heap ops sur 1000 curseurs vs increment trivial).

### Take-away

La chaîne complète **build → convert → query** maintient maintenant le pic RAM privée **sous 250 KB au query** et 13 MB au convert. C'est la première fois qu'on a la même architecture validée à 1M et théoriquement scalable à 1B sous le budget.

## Phase 4 : io_uring batched IO (test sous cgroup réel)

### Pourquoi
Test sous `sudo systemd-run --scope -p MemoryMax=200M -p MemorySwapMax=0` a révélé que la query devenait **15.7 secondes par query** sous 200 MB cap (vs 54 ms sans cap). Le mmap synchrone faisait 1500 page faults séquentielles par query, chacune attendait la précédente → SSD sous-utilisé (queue depth = 1).

### Solution : `io_uring` batched

Modifications :
- `Forest.ring` (struct io_uring) initialisé une fois dans `forest_open`, libéré dans `forest_close`. Heap-alloué dans main pour stabilité d'adresse.
- `rerank_l2_uring` : submit les 500 lectures de vecteurs SIFT en batch (1 io_uring_submit), reap en arrivée.
- `forest_collect_topn` réécrit en **prefetch-then-merge** : pour chaque arbre, submit le root block via io_uring ; au reap, append au `TreeChain` en RAM, submit le `block.next` si chaîné. Plusieurs phases (typiquement 1-2). Une fois toutes les chaînes en mémoire, K-way merge classique.
- Les fichiers `.bks` ne sont plus accédés via mmap au query : io_uring lit via `fd` direct → **pas de pages mappées dans le process RSS**.

### Résultats sous **cgroup 100M, no swap**, 1000 trees × depth 18 × sub16 × v3 (SIFT 1M)

| Variante | recall@10 | ms/q | peak ru_maxrss | RssAnon | RssFile (mapped) |
|---|---|---|---|---|---|
| sync mmap + cgroup 200M | 99% | 15 700 | 239 MB | 0.2 MB | 234 MB |
| **uring + cgroup 100M** | **99.80%** | **1 048** | **47 MB** | 3.2 MB | 2 MB |
| uring sans cgroup | 99.70% | 537 | 49 MB | 2.5 MB | 2 MB |

**15× speedup** sous cap dur, recall préservé, RAM totale **47 MB** (sous le cap de 100 MB demandé).

### Pourquoi `mapped` chute à 2 MB

io_uring lit via `fd` direct dans des buffers heap (`temp[nt]` pour les blocks, `big[n_cands*dim*4]` pour les vecteurs). Les pages OS chargées par le kernel passent dans le page cache **système-wide** mais ne sont **plus mappées dans l'adressage du process** → `RssFile` reste à ~2 MB (juste le code + libs).

Conséquence : `peak ru_maxrss` devient une mesure honnête du coût RAM du process — plus de gros bias "mmap me masque le coût réel".

### Validation de l'objectif principal

```
"RAG quasi-zéro RAM, cible 1B+ docs sous 100 MB"
                                              ↑
                                       atteint à 47 MB sur SIFT 1M, sous cgroup hard
```

Pour scaler à 1B docs :
- working set par query = ~1500 random reads (constant en n_docs, déterminé par n_trees)
- io_uring batche → 1500 / queue_depth ~ peu importe le scale du dataset
- chaque query = 4-5 MB de working set transitoire en cache OS
- → même latence ~1 s/q sous 100 MB cap à 1B docs

### Sweep cgroup caps (cold cache, 100 q chacun)

| cap | recall@10 | ms/q | peak RSS |
|---|---|---|---|
| 100 MB | 99.80% | 1 048 | 47 MB |
| 500 MB | 99.80% | 913 | 46 MB |
| 1 GB | 99.70% | 918 | 45 MB |
| 1.5 GB | 99.60% | 1 018 | 47 MB |
| 2 GB | 99.70% | 1 275 | 49 MB |
| no cap (hot, biaisé) | 99.70% | 537 | 49 MB |

**Latence essentiellement plate à ~1 sec/q de 100 MB à 1 GB.** Le process ne consomme jamais > 49 MB ; le cache au-delà de ~500 MB ne sert à rien parce que chaque query touche ~1500 pages **différentes** (queries aléatoires → cache d'une query inutile pour la suivante).

Le bottleneck est **SSD-bound** sur les random reads, pas RAM-bound. Conséquence pratique :
- inutile d'allouer beaucoup de RAM à ce service en prod
- une instance avec 100-500 MB est aussi rapide qu'une instance avec 2 GB
- la latence est déterminée par le NVMe sous-jacent

Estimation 1B docs : working set inchangé (constant en n_trees), latence projetée **~1-2 sec/q** indépendamment du cap, dégradation modeste vs 1M parce qu'il faut juste 1000× plus de feuilles sur disque mais on lit toujours le même nombre.

# Mise à jour — jeudi 14 mai 2026

## Phase 5 : counting-sort sparse layout (remplace les blocks)

### Pourquoi on abandonne les blocks chaînés

Cadrage scaling 1B docs / 1024 trees / **depth 30** / budget 300 MB RAM / 8 TB disque :

| Structure | À 2^30 | × 1024 trees |
|---|---|---|
| `root_block` dense (1 block × leaf) | 32 GB/tree | **32 TB** ✗ |
| `count[2^depth]` (counting sort dense) | 4 GB/tree | — ✗ build RAM |
| `offset_table[2^depth]` dense | 4 GB/tree | **4 TB** ✗ |

Le design blocks d'aujourd'hui **pré-alloue un root block par feuille même vide** → 63 % de feuilles vides (Poisson) → 20 TB gaspillés. Inacceptable à 1B.

Décision : on passe à **sparse layout via counting sort externe**. Pas de pré-allocation.

### Format `.srt` par arbre

```
[16 B header]      magic "SRT1" | n_leaves | total_docs | reserved
[offsets table]    (n_leaves + 1) × uint32   — doc-index cumulatif
[data]             total_docs × uint32        — doc_ids triés (par leaf, puis par doc_id)
```

Pour la feuille X : `offsets[X..X+1]` donne `(start, end)`. Posting list = `data[start..end)`.

### Build (convert phase)

Per tree, 2 passes sur le pair-file :
1. **Pass 1** : count par leaf → `count[n_leaves]`. RAM = `n_leaves × 4 B`.
2. **Cumulatif** → `offsets[0..n_leaves]`, copie en `pos[]` pour le tracking.
3. **Pass 2** : re-scan, écrit chaque `doc_id` à `data[pos[leaf]++]`.

À 1M / d18 : RAM convert = 1 MB count + 1 MB offsets + 4 MB data = **~6 MB/tree** (vs 13 MB blocks).

### Query — 2-phase io_uring

Plus de chain-walk. Chaque arbre = 2 reads :
- **Phase 1** : `1024 × 8 B` reads de `offsets[X..X+1]` → connait `(start, length)` pour chaque arbre.
- **Phase 2** : `1024 × variable` reads des posting lists (taille exacte par arbre).

Total ~2048 reads en 2 phases (vs ~3000 reads en 3-4 phases avec blocks). K-way merge sur les posting lists déjà triées, inchangé.

### Résultats SIFT 1M, 1000 trees × d18 × sub16 × v3, 1000 queries

| Métrique | Blocks (Phase 4) | **Sorted (Phase 5)** | Δ |
|---|---|---|---|
| Recall@10 | 99.80 % | **99.77 %** | ≈ |
| Latence cgroup 100M | 1048 ms/q | **70.3 ms/q** | **×15** |
| Latence cgroup 300M | — | 70.8 ms/q | identique |
| Build wall-clock | 4:30 min | 4:30 min | ≈ |
| Build peak RSS | 27 MB | **10 MB** | -63 % |
| Query RssAnon | 3.2 MB | 24 MB | +21 MB (K-way buffers sur posting lists) |
| Query peak RSS total | 47 MB | **53 MB** | + 6 MB |
| Disque total | 7.5 GB | **4.8 GB** | -36 % |

### Lecture des résultats

- **×15 sur la latence sous cap dur** : le coût "chain-walk SSD-bound" disparaît. 2 phases au lieu de 3-4 phases → SSD mieux utilisé.
- **Latence plate entre cgroup 100M et 300M** (70.3 ms vs 70.8 ms) → plus du tout RAM-bound, on est passé en régime "drive saturé en 2 phases". Cap moins serré n'aide pas.
- **RssAnon monte à 24 MB** (vs 3 MB blocks). Honnête : K-way merge alloue les posting lists en RAM (~10-20 KB/tree × 1024 trees + cursors + scratch). C'est de la RAM privée mesurée par /proc, pas du mmap caché. Toujours largement sous 300 MB.
- **Build wall-clock identique** : à 1M le sort externe se réduit à un counting in-RAM, négligeable.

### Implications scaling 1B

- RAM query scale linéairement en `n_trees`, **pas en `n_docs`** → ~24 MB à 1024 trees reste constant.
- Build à 1B : counting in-RAM impossible (count[2^30] = 4 GB) → **external merge sort** nécessaire, ~24 GB IO/tree, **~5-6 h wall-clock total** pour 1024 trees.
- Disque final estimé 1B/d30/1024 trees : ~5-7 TB avec varint deltas (sous 8 TB).
- Latence query estimée : phase 1 + phase 2 ~150-300 ms/q à 1B (limité par drive IOPS sur ~2048 random 4 KB reads).

Réduire `n_trees` (256-512) **ne tient pas** : le recall chute (sweep antérieur, validé hors session). Le levier "moins d'arbres" n'est pas dispo. La voie restante pour viser 50 ms : drive plus rapide, ou compression varint des posting lists pour réduire la taille des reads phase 2.

## Préparation dataset SIFT 10M

### Source

`datasets/sift10M/sift10m.hdf5` (10.7 GB) — téléchargé depuis Hugging Face. Format : benchmark **filter-ANN** à 6 labels par doc + ranges par query.

| Dataset HDF5 | Shape | Dtype | Usage |
|---|---|---|---|
| `train_vec` | (9 991 000, 128) | float64 | corpus à indexer (SIFT classique, valeurs 0-214 stockées en double) |
| `train_label` | (9 991 000, 6) | int64 | 6 labels par doc — **ignorés** (notre pipeline = ANN pur) |
| `test_vec` | (10 000, 128) | float64 | queries |
| `test_label` | (10 000, 6, 2) | int64 | ranges filtre par query — ignorés |
| `neighbors` | (10 000, 200) | int64 | GT **filtré** — inutilisable pour ANN sans filtre |
| `distances` | (10 000, 200) | float64 | distances GT filtrées |

### Pourquoi le GT du HDF5 ne sert pas

Vérifié explicitement sur query 0 :
- Notre NN brute-force (sans filtre) : doc `1424740`, distance L2 = **89.10**
- GT HDF5 NN0 (filtré) : doc `6638208`, distance L2 = **140.55** (cohérent, distance filtrée ≥ non-filtrée)
- Overlap top-10 unfiltered vs filtered = **1/10**

→ il fallait recalculer un GT non-filtré pour évaluer notre pipeline ANN. Décidé 250 queries pour débuter (≈ ±1-2 % de bruit sur recall@10, suffisant pour valider).

### Pipeline de conversion : `datasets/sift10M/prepare.py`

Un script Python en 3 étapes, idempotent (saute ce qui existe) :

1. **Convert** `train_vec` (float64) → `sift10m_base.fvecs` (float32, format fvecs standard) : **5.15 GB**
2. **Convert** `test_vec` (float64) → `sift10m_query.fvecs` (10 000 × 128 float32) : 5.16 MB (on garde les 10K pour pouvoir scaler plus tard sans relancer)
3. **Brute-force GT** sur les 250 premières queries → `sift10m_groundtruth.ivecs` (250 × 100 int32) : **101 KB**

Brute-force GT : matmul numpy par chunks de 500K vecteurs (qsq + csq − 2·Q·Cᵀ), argpartition top-100 par chunk, merge sur top-100 cumulatif. **~158 sec** sur 20 cœurs pour 250 queries × 9.99M docs.

### Compatibilité avec recall.c

`recall.c` lit le GT en format `[int32 dim=100][100 × int32 ids]` par query (`GT_K=100` hardcoded). Donc le `.ivecs` produit est directement consommable par `cmd_recall`/`cmd_topn` sans modification du code.

### Inventaire `datasets/sift10M/`


Décision : `depth = ⌈log₂(n_docs)⌉` plutôt que la config 1M (d18). À 10M, log₂ ≈ 23.25 → **depth 23 = 2^23 = 8.39 M feuilles/arbre, 1.19 docs/leaf moyenne**.

|---|---|---|---|

**Peak build RSS 106 MB** = exactement les `count[2^23] + offsets[2^23+1] + data[n_docs]` = 32 + 32 + 40 MB. Sous le budget 300 MB, mais c'est le moment où le counting dense commence à serrer. À 1B/d30 il faudra passer à du counting sparse via bucket-partition (déjà documenté en Phase 5).

**Inflation disque (+48 % par doc indexé)** : à depth 23, l'offset table prend 44 % des bytes par tree (32 MB offsets / 72 MB total) contre 20 % à d18. C'est le coût du choix `depth = log₂(N)` — feuilles très fines donc table très grosse.

### Résultats query (250 queries, cgroup 300M)

|---|---|---|---|---|
| 500  | 97.72 % | 130.2 | 30.3 MB | **77.7 MB** |

| 2000 | 98.96 % | 150.5 | 31.1 MB | 79.0 MB |

**Latence × 1.86 vs 1M** (70 → 130 ms à top_n=500). Pas constante comme espéré — probablement parce que la zone offset_table totale fait 32 GB sur disque (32 MB × 1024 trees), bien au-delà du page cache OS disponible sous cap 300M. Donc plus de cold-cache reads que prévu.

**Recall plafonne ~99 %** avec top_n élevé (gain marginal 1000→2000 = +0.4 pt). C'est le plancher inhérent à la sparseness 1.19 doc/leaf : trop peu de docs/leaf pour avoir un signal de co-occurrence robuste. La voie pour revenir > 99.5 % serait de baisser à **depth 22** (2.4 docs/leaf), au prix d'un disque ~2× plus petit (offsets / 2) — à tester si on veut du recall publiable.

### Apprentissages SIFT 10M

1. **Peak RAM build scale en `2^depth`, pas en `n_docs`.** L'arithmétique counting+offsets domine la data section dès qu'on est à 1+ doc/leaf en moyenne. À d23, RAM build = 64 MB pour les indices + 40 MB pour la data = 60 % d'overhead structurel.
2. **Latence query scale légèrement super-linéaire** quand le drive cache ne suit pas. À 10M / d23, l'offset table totale (32 GB) ne tient pas dans le cache OS sous cap 300M → plus de IO réels.
3. **Recall plafonne avec la sparseness des feuilles.** À 1.19 doc/leaf, depth-23 n'arrive plus à isoler le voisinage. Trade-off classique recall ↔ taille_d'index : aller plus dense (d22 ou moins) = recall meilleur + index plus compact + latence + faible, au prix d'un build plus rapide.
4. **top_n vs recall donne 0.5-1 pt mais plafonne** : doubler les candidats à reranker n'est rentable qu'en partie quand l'arbre lui-même rate les vrais NN.

## Phase 6 : sparse offset table + multi-index famille

### Format `.srt2` (sparse offsets)

Décision : passage à un format sparse pour permettre le **multi-index** (plusieurs sous-corpora partageant les seeds peuvent être requêtés ensemble comme un seul index).

```
[24 B header]   magic "SRT2" | depth | n_nonempty | total_docs | stride | reserved
[n_samples × 4 B]   sample_leaf_ids (stride entries on disk = 4 KB window)
[n_nonempty × 8 B]  (leaf_id, offset) triés ascendant par leaf_id
[8 B sentinel]      (0xFFFFFFFF, total_docs) — même taille qu'une entrée index
[data: total_docs × uint32]  doc_ids triés par leaf
```

**Stride adaptatif** au build : `max(512, n_nonempty / 65536)`. Limite les samples RAM à ~50 MB total au 100M scale.

**Sample table** chargée en RAM à l'open (small) : binary search sample → narrow à 1 bucket → 1 disk read de 4 KB → binary search RAM dans le window.

### Apprentissages structurels

- **Sparse n'est pas toujours plus petit que dense** : sparse = `n_nonempty × 8 B`, dense = `n_leaves × 4 B`. Sparse gagne seulement si non-empty < n_leaves / 2 (≈ < 0.7 docs/leaf).
- Pour SIFT 1M / d=18 / sub_dim 16 v3 : 26K non-empty / 262K leaves = 10 % → sparse gagne (4.0 GB vs 4.8 GB dense, -17 %).
- À d=22 / 1B combinés (target multi-index 100 × 10M) : ~80 % non-empty → sparse perd vs dense, mais on garde sparse pour la flexibilité multi-corpora petits.

### Décisions projet

1. **Depth fixé à 25 pour les nouvelles familles multi-index** (ou 22 pour les tests intermédiaires). NE PAS aller à d=40 "pour la flexibilité" — la recall en query natif d40 s'effondre car les votes deviennent uniforme-1 (cf. memory `feedback-depth-vote-discrimination`).
2. **delta encoding deltas** dans la data section : viable à 1M scale (40 % de gain) mais marginal au 100M+ scale. Différé.
3. **Format `.srt2` validé** : SIFT 1M sparse → 97 ms/q recall 99.77 % (vs dense 70 ms 99.77 %, -27 % latence pour la flexibilité).

### Code multi-index (Phase 7)

`forest_collect_topn_multi(Forest** forests, int n_forests, ..., int query_depth, ...)` :
- Traverse une seule fois (les seeds sont partagés entre forests).
- Pour chaque tree, lookup window dans CHAQUE forest (2 reads/forest pour low/high bornes).
- Concat des posting lists par tree (chaque forest stocke des global doc_ids disjoints).
- `qsort` du buffer par tree (concat de plusieurs sources → non-monotone).
- K-way merge inter-tree.

**Piège résolu :** `io_uring_wait_cqe` BLOQUE sur ring déjà drainé. Solution : tracker `per_ring_subs[fi]` et reap exactement ce nombre par ring.

**Piège FD :** N_forests × N_trees = 4 × 1000 = 4000 FDs, dépasse la limite par défaut 1024. Raise via `setrlimit` AVANT `forest_open`.

**CLI :** `--doc_offset N --doc_count N` au build pour shifter les doc_ids (préserve l'unicité globale entre sous-corpora). `multitopn idx_a,idx_b,...` au query.

# Phase 8 — Expérience "build au max possible" (samedi 16 mai 2026, suite)

## Contexte

Question stratégique : faut-il builder à la depth la plus haute possible pour avoir la flexibilité "query au depth de son choix" au runtime ? Tests empiriques sur SIFT 1M et SIFT 10M multi-index.

## Refactor int64 (max depth débloqué de 30 → 64)

**Limite int32 atteinte à d=30** : `Pair.leaf_id` et `traverse() return` étaient `int32_t`. À d=31+ : overflow → leaf_ids garbage.

**Refactor int64 :**
- `Pair.leaf_id` : int32 → int64 (Pair = 16 B aligned vs 8 B)
- `SparseEntry.leaf_id` : uint32 → uint64 packed (12 B vs 8 B)
- `traverse() / traverse_sub() / leaf_base() / leaf_count() / node_seed() / pick_dims()` : int32 → int64
- `Forest.leaves_buf`, `low_leaf`/`high_leaf` locals : tous uint64
- Bump magic SRT2 → SRT3

**Bug subtil corrigé pendant refactor** : `uint32_t target = (slot == 0) ? low_leaf : high_leaf;` truncate la cible 64-bit à 32 bits. Recall artif s'effondre à 8 %. Fix : `uint64_t target`. À 2 endroits dans `query_tree.c`.

## Mesures à SIFT 1M sub_dim 16 v3 1000 trees

| | d=18 (baseline) | d=30 (int32 max) | **d=40 (int64)** |
|---|---|---|---|
| Build wall | ~5 min | ~8 min | ~10-12 min |
| Disque (1 index) | 4 GB | 6 GB | 11 GB |
| Peak RSS build (convert) | 10 MB | 10 MB | 33 MB |
| Peak RSS query | 36 MB | (n/a) | 45 MB |
| Native recall, top_n=500 | 99.76 % | 93.12 % | 69.48 % |
| Native recall, top_n=4000 | 99.76 % | **97.64 %** | 81.12 % |
| Native latency | 72 ms | **11 ms** | **8 ms** |
| Artif qd=18 recall | (= native) | (skip) | **99.76 %** |
| Artif qd=18 latency | (= native) | (skip) | 157 ms |

→ Recall à qd=18 sur d=40 build = strictement identique à native d=18 build. **Le math marche, le code est correct**, l'artificial qd est mathématiquement équivalent à un build natif au depth cible (les hyperplans aux niveaux 0..qd-1 sont identiques par les mêmes seeds).

## Mesures multi-index SIFT 10M (4 sous-corpora 5M+3M+1.5M+0.5M)

| | **d=22 (sweet spot natif)** | **d=40 (build haut + qd=22 artif)** | Δ |
|---|---|---|---|
| Recall@10 top_n=500 | 98.08 % | 98.08 % | **identique** |
| Recall@10 top_n=1000 | 99.08 % | 99.08 % | identique |
| Recall@10 top_n=2000 | 99.40 % | 99.40 % | identique |
| Latence query top_n=500 | 149 ms | 262 ms | **+75 %** |
| Peak RSS query | 128 MB | 244 MB | +91 % |
| Disque total | 43 GB | **117 GB** | **+170 %** |
| Build wall total | ~50 min | ~113 min | +126 % |

→ La flexibilité d=40 coûte cher : +75 % de latence permanente sur toutes les queries, ×2.7 disque.

## Pourquoi le disque grossit ×2.7 et pas ×1.5 (uint64 simple) ?

Décompose le coût disque par doc :

| Composant | d=22 (uint32) | d=40 (uint64 packed) |
|---|---|---|
| Sparse_index entry | 8 B | 12 B (×1.5) |
| Avg docs/leaf non-vide (sub_dim concentration) | ~7 | ~1.25 (chaque doc seul) |
| Sparse overhead per doc | 8/7 = 1.14 B | 12/1.25 = 9.6 B |
| Data per doc | 4 B | 4 B |
| **Total per doc** | **5.14 B** | **13.6 B** |
| Ratio | 1.0 | **×2.65** |

Le dominant : à d=40 chaque doc tend à être seul dans son leaf → **6× plus d'entrées sparse_index par tree**. Combiné avec le +50 % par entry du packing = ×9 sur la sparse_index seule. La data section reste constante donc le ratio total ressort à 2.65.

## Décision projet

**Reste à depth ≤ 30** :
- d=30 sweet spot pour 1B docs (target principal) avec marge de 100× via query_depth artificiel
- Pas de uint64 nécessaire (int32 = depth max 30)
- Coût query natif d=30 = 11 ms / 97.6 % top_n=4000 (excellent fast lane)
- Coût query artificiel d=18 sur d=30 = ~130 ms / 99.7 % (premium lane)
- Disque 1B reste sous 6 TB à d=30 (vs 12 TB à d=40)

**Si on doit aller au-delà de 1B combiné** (100B target) : on rebuild plus tard. Le rebuild d'un shard 1B = 6h, acceptable.

**Next step : delta encoding sur sparse_index** (économise ~25 % du disque à d=30, jusqu'à 3.5 TB sauvés au 1B). À implémenter après revert int64 → uint32.

## Pre-filter par bitmap

### Motivation

Pour les queries avec contrainte de métadonnées (e.g. "articles fr publiés après 2023") : l'application résout les métadonnées en une liste de doc_ids autorisés. Le forest doit filtrer ses candidates en RT.

### Implémentation

Version 1 — sorted array + bsearch : O(log M) check, ~70 ns par doc. Au 1M test, +5-10 ms par query.

Version 2 — **bitmap (final)** : O(1) check, ~1 ns par doc.
- 1 bit par doc dans le corpus → N/8 bytes total
- Set bit i : `bitmap[i>>3] |= (1 << (i&7))`
- Test bit i : `(bitmap[i>>3] >> (i&7)) & 1`
- Construit côté app (ou via CLI `--filter <binfile>` avec liste int32)
- Inséré dans le K-way merge avant le push to top_n heap

| Scale | Bitmap size | Construction time | Per-doc check |
|---|---|---|---|
| 1M | 125 KB | < 1 ms | ~1 ns |
| 100M | 12.5 MB | ~5 ms | ~1 ns |
| 1B | 128 MB | ~50-100 ms | ~1 ns |
| 10B | 1.25 GB | dépasse 800 MB cgroup | — |

Pour 10B+ : roaring bitmap (sparse hybride) à considérer plus tard.

### Auto-depth heuristic

Décidé : exposer un mode `--auto_qd` qui calcule `qd = log2(M) - log2(K)` où K = nombre cible de filter-matches par super-leaf (default K=4 → qd=log2(M)-2 comme proposé).

Formule à l'app : transmettre `n_filter_ids` à la query → wrapper auto-derive qd.

Pour build_depth = log2(N) (sweet spot) :
- M=1B (no filter) : qd≈28-30
- M=1M filter : qd≈18
- M=10K filter : qd≈12
- M=100 filter : qd≈5

Donne ~4 matches per super-leaf per tree systématiquement.

### Résultats SIFT 100M, filter de 508K ids (0.5 % du corpus)

| Mode | Recall@10 | Latence | Filter overhead |
|---|---|---|---|
| Native qd=30 no filter | 90.90 % | 295 ms | — |
| **Filter (0.5 %) qd=30** | **99.10 %** | **289 ms** | **0 ms** (gratuit !) |
| qd=25 top_n=2000 no filter | 99.10 % | 887 ms | — |
| Filter + qd=25 + top_n=2000 | **100.00 %** | 869 ms | -18 ms (gratuit) |

**Insight pratique :** ajouter un filter modérément dense (0.1-1 %) au native qd =
- Boost recall significatif (90.9 → 99.1 %)
- **Zéro pénalité latence** (le bitmap check est négligeable)
- Pas besoin de descendre qd

Le bitmap est l'interface idéale : le COÛT QUERY ne dépend PAS de la taille du filter. Le filter ne SOUSTRAIT pas du travail, mais il enlève les distractions du candidate pool, ce qui paradoxalement aide le recall.
