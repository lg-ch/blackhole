## J4 — Recall investigation + signal observable

**Question** : pourquoi à dim=768 on doit baisser qd de 6 niveaux sous build_depth pour 99 % recall, alors que SIFT à dim=128 atteint 99 % à qd native ?

### Diagnostic

| Dataset | dim | sub_dim/dim | R∞ à qd native | qd pour 99 % |
|---|---:|---:|---:|---:|
| SIFT 1M | 128 | 12.5 % | 0.998 | native |
| arxiv 2M | 768 | 2.1 % | 0.836 | build − 6 |

À sub_dim=16/dim=768 (2.1 % des dims), les hyperplanes RP routent quasi-aléatoirement → la query et ses NN partent dans des leaves différentes dès les premiers niveaux. R∞ native plafonne à 0.84 (16 % des NN structurellement invisibles aux 1000 leaves natives visitées). Sur SIFT, 12.5 % des dims suffisent à co-router query+NN dans les mêmes leaves.

### Signal observable au query time : `n_distinct_cands`

Le K-way merge visite N candidats distincts. Mesuré sur arxiv :

| qd | n_distinct | %corpus | recall |
|---:|---:|---:|---:|
| 20 native | 13 648 | 0.66 % | 0.667 |
| 16 | 123 598 | 6.0 % | 0.917 |
| 14 | 354 945 | 17.2 % | 0.973 |
| 12 | 897 830 | 43.6 % | 0.994 |

Pour SIFT à qd native : 434 380 distincts (43.4 % du corpus) → recall 0.998. **Règle empirique : visiter ~40 % du corpus → recall ≥ 0.99**, quel que soit le dataset.

### `--auto_qd_v2` : autocalibré 2-probes

```
probe0 = avg_distinct(qd = build_depth, 5 queries)
probe2 = avg_distinct(qd = build_depth - 2, 5 queries)
factor = (probe2 / probe0)^(1/2)
qd_target = build_depth − ceil(log(target / probe0) / log(factor))
target = ratio × N_pool  (N_corpus sans filter, filter_card avec)
```

Validation cross-dataset (un seul flag) :
- arxiv : factor=1.74 mesuré → qd=12 → recall 0.994 / 92 ms
- SIFT : factor=1.10 (saturé) → qd=18 native → recall 0.998 / 75 ms
- arxiv + filter 2 % : qd=12 → recall 0.945 / 48 ms
- arxiv + filter 0.8 % : qd=12 → recall 0.766 / 50 ms (plafond intrinsèque)

## J5 — Filter-aware K-way merge

**Problème** : le bitmap au hot path gate uniquement le rerank L2. Le K-way merge itère tous les vote-events lus du disque, peu importe le filter. À 1 B docs scale, qd=12 → 256 M vote-events par query, inacceptable.

**Fix** : `cursor_seek_allowed` dans `query_tree.c`. Iterator roaring persistent par tree (forward-monotonic) + binary search dans `c->docs`. Le merge skip aux ranges allowed, ne traverse plus que les docs du filter.

Mesures (filter 2 %) :
- qd=12 : 91 → **48 ms** (-47 %), recall identique
- qd=10 : 303 → **165 ms** (-46 %)
- qd=8 (filter 0.8 %) : 1060 → **622 ms** (-41 %)
- no_filter : 0 % régression

`avg_distinct` au merge passe de 898 k → 18.6 k sur filter 2 % à qd=12 (= taille effective filter × ratio visited). Le merge ne traverse littéralement plus que les docs du filter.

**Plafond résiduel** : I/O des leaves (io_uring lit toutes les super-leaves indépendamment du filter). Pour scaling 1 B faut filter-aware I/O en plus.

**Note importante** : ce change a modifié la sémantique de `n_distinct` (= "distincts allowed visités" au lieu de total). L'auto_qd_v2 a dû être ajusté en conséquence : `target = ratio × filter_card si filtre`.

## J7 — Compensation sub-corpus dans auto_qd_v2

Découverte : la formule `target = ratio × filter_card` corrigée donne qd=12 dans tous les cas (no_filter, 2%, 0.8%) car le ratio probe/target reste constant. Mais le recall absolu chute sur filter sparse (forest sub-optimal sur sub-corpora arbitraires).

Heuristique user (validée empiriquement) : descendre qd de `extra_levels = floor(log2(N_corpus / filter_card)) - 1` niveaux supplémentaires :

| Filter | density | extra | qd_final | Recall (sans → avec) |
|---|---:|---:|---:|---:|
| year=2007 | 2% | 4 | 8 | 0.945 → **0.999** |
| cs.LG | 0.8% | 5 | 7 | 0.766 → **0.988** |
| no_filter | 100% | 0 | 12 | 0.994 (inchangé) |

CLI : actif par défaut avec `--auto_qd_v2 + filter`, désactivable via `--no_filter_compensate`.

**Trade-off** : recall remonte mais latence ×12-24 (612 ms / 1206 ms sur arxiv 2M). Sur ce calibre, **bruteforce reste préférable**. La compensation prend tout son sens à plus grande échelle (subset > 5 GB où BF impossible).

**Routing final propre** :
- subset < 50 MB → bruteforce (recall 1.0, <80 ms)
- 50 MB - 5 GB → forest + auto_qd_v2 + compensation (recall ~0.99)
- > 5 GB → forest + auto_qd_v2 + `--no_filter_compensate` (best effort)

## J8 — Compensation mode 2 (formule alternative `/2`)

Proposition user : `extra = floor(log2(N/F) / 2)` au lieu de `floor(log2(N/F)) - 1`. Donne ~moitié des levels → moitié du coût latence.

Validation arxiv 2M :

| Filter | Mode 1 (−1) | Mode 2 (/2) | BF |
|---|---|---|---|
| year=2007 (2%) | qd=8, 0.999 / 607 ms | qd=10, **0.991 / 163 ms** | 0.999 / 77 ms |
| cs.LG (0.8%) | qd=7, 0.988 / 1198 ms | qd=9, 0.933 / 325 ms | 1.000 / 34 ms |

Verdict : Mode 2 = bon compromis pour filter ~2% (−0.008 recall, /3.7 latence). Pénalise filter ultra-sparse (cs.LG : −0.055 recall). CLI : `--filter_comp_mode 2`.

## J9 — Multi-index avec qd auto par forest (implémenté)

### Design implémenté

Nouvelle commande `rpforest multitopn_auto` qui :
1. Ouvre N forests (même API que `multitopn`).
2. **Probe auto_qd_v2 par forest** (2 probes × 5 queries chacun), calcule `qd_i` indépendamment pour chaque sous-corpus.
3. Pour chaque query, appelle `forest_collect_topn` séquentiellement par forest avec son `qd_i`.
4. Merge N × top_n candidats par sort + dedup (somme des votes par doc_id), garde top_n globaux par votes.
5. Rerank L2 contre base.fvecs partagé.

CLI : `./rpforest --auto_qd_v2 multitopn_auto <q> <gt> <base> <idx1,idx2,...> <n_trees> <depth> [top_k top_n n_q]`. Compatible avec `--filter_ch`, `--filter_comp_mode`, `--no_filter_compensate`.

### Trade-off d'implémentation

**Voie B** (choisie) : N appels séquentiels à `forest_collect_topn`. Simple, mais perd l'efficience pairwise-seed (traversée des trees dupliquée N fois).

**Voie A** (TODO) : refactor `forest_collect_topn_multi` pour accepter `qd_per_forest[]`. Traversée unique jusqu'à `max(qd_i)`, dérivation des leaf_id_i par bit-shift, K-way merge sur cursors hétérogènes. Préserve l'efficience pairwise mais ~150 lignes de refactor.

### Quand utiliser

Pertinent quand les sous-corpora ont des **profils statistiques différents** (factor_per_level, dispersion intrinsèque). À pairwise-seed sur sous-corpora homogènes (mêmes propriétés), tous les `qd_i` convergent et un seul `qd` global suffit.

Cas concrets où ça matters :
- Multi-modal : forest texte + forest images (dim/sub_dim/embeddings très différents).
- Tailles très inégales : 1 forest 10M docs + 1 forest 100k docs → besoin de qd différent.
- Filter présent → compensation par forest selon density locale.

### Smoke test sur single forest

`./rpforest --auto_qd_v2 multitopn_auto ... index_arxiv` → qd=12, recall 0.994, 97 ms. Cohérent avec single forest path.

### Bench 2 partitions arxiv (chacune 1M docs, depth=19, sd16 gen v3)

| Setup | qd | Recall | Latence |
|---|---|---:|---:|
| Single full forest (depth=20) | qd=12 (auto) | 0.994 | 92 ms |
| Multi-auto 2 partitions | f0=12, f1=11 (auto/forest) | 0.991 | **136 ms** |
| Multi-classic (single qd) | qd=11 (manual) | 1.000 | 164 ms |

**Concept validé** : qd auto par forest fonctionne, multi-auto −17% latence vs multi-classic à recall comparable.

- **`meta.txt` stocke `n_docs = doc_offset + n_vecs`** (au lieu de `n_vecs` réel). Sur partition p1 (1M docs avec offset 1M), `n_docs=2058751` au lieu de 1029376 → auto_qd_v2 voit "2M" → choisit qd 1 niveau plus profond. ## À explorer (futur) — Multi-index pairwise-efficient avec qd auto par forest

Le multi-index actuel (`forest_collect_topn_multi`) utilise UN seul `query_depth` global pour tous les forests partageant les seeds. Mais avec la formule `n_distinct → qd_target` validée, **chaque forest devrait avoir son propre qd**, calculé dynamiquement selon sa taille / profil.

Idée : sur un setup multi-index avec N forests partitionnés (e.g. 10 × 100 M docs), la query passe par chaque forest. Si les sous-corpora ont des dispersions différentes (factor_per_level qui varie), il faut ajuster qd par forest pour que la contribution de chaque forest au pool merge soit cohérente.

Design proposé :
1. Pour chaque forest f_i : 2-probe au build_depth_i → factor_i, n_distinct_native_i.
2. Cible globale = `top_n × ratio_overshoot` (à définir).
3. Distribuer la cible par forest proportionnellement à N_docs_i.
4. Calculer qd_i par forest via la formule classique.

Considération pairwise-seed : les forests partagent les hyperplanes, l'alignement des leaves natives entre forests est préservé jusqu'au min(qd_i). Au-dessus du min, certains forests voient des super-leaves plus larges → votes asymétriques mais corrects.

Implémentation : refactor `forest_collect_topn_multi` pour accepter `query_depth_per_forest[]` (ou faire N appels parallèles à `forest_collect_topn` + merge externe).

À faire quand on attaquera un vrai multi-index (e.g. arxiv partitionné par year-buckets).
